# 8. Actions, graphs, and incremental builds

[Previous: Targets](07-projects-and-targets.md) · [Contents](README.md) · [Next: Configuration](09-configuration.md)

## 8.1 Define deferred work

This complete `Rattspec` copies an input file through a helper function:

```ratt
project(name: "copy", version: "1.0.0", kind: "single")
import "fs"

fn decorated(value: str) -> str { return value + "\n" }
let result = rule(name: "result", output: "build/result.txt",
                  inputs: ["input.txt"])
action(result) {
  fs.write("build/result.txt", decorated(fs.read("input.txt")))
}
```

During construction, the declaration and helper definition run, while the action
body is captured. During execution, the body reads the input and writes the
output if the action is stale.

`action(result)`, `action result`, and an untargeted `action { ... }` are parsed
forms. An untargeted block attaches to the most recently declared target in its
spec evaluation. Explicit handles make attachment clear, particularly in loops
and helper functions. One target may have at most one deferred action block.

A target can contain an explicit `command:` and a deferred block. The scheduler
runs recorded commands first, then the Rattscript body. Without either, a custom
rule is invalid. A compiled target with no custom execution receives automatic
compiler commands.

## 8.2 Capture semantics

Deferred execution serializes the action's AST and lexical environment. This
includes user-function bodies, recursive closures, collection object identities,
target/package handles, and supported native bindings. An action does not retain
a running construction evaluator.

Scopes are serialized when declarations are lowered after spec discovery, not
as a textual macro expansion at the `action` statement. Lexical mutations made
during construction can therefore affect the captured state. Prefer completing
the values an action needs before declaring its work, and avoid using mutable
construction state as an implicit ordering mechanism between different targets.

Each execution gets a thawed environment. Mutating a captured list inside one
action is local to that execution; it does not update another action's captured
environment. Shared identities within one snapshot are preserved.

Configuration is captured with the action separately. A later user-config edit
does not alter a frozen action's `env.get` results. Reconstruct or re-export the
graph to capture changed settings.

## 8.3 Track every execution input

The scheduler cannot observe arbitrary reads performed by a subprocess or user
function. Declare every file whose change should cause the action to rerun.

| Field | Tracking behavior |
| --- | --- |
| `sources` | Tracked inputs and, for automatic compilation, source arguments |
| `inputs` | Extra tracked files |
| `headers` | Extra tracked files with header-oriented naming |
| `raw_inputs` | Tracked original files without automatic `.in` output generation |
| `deps` | Named prerequisites and their output files |

`sources`, `inputs`, and `headers` ending in `.in` are turned into configuration
actions producing the filename without `.in`. `raw_inputs` retain the original
template filename and byte identity.

If an action itself calls `fs.read("message.in")`, that read renders the
template in memory. Track the template as `raw_inputs: ["message.in"]` if the
action should keep that explicit rendering behavior. Otherwise the normal
input configurator produces and tracks `message`.

An input can be generated by another target. Its producer is an implicit
prerequisite even when no `deps:` field names that producer:

```ratt
let first = rule(name: "first", output: "build/first.txt")
action(first) { fs.write("build/first.txt", "first") }

let second = rule(name: "second", output: "build/second.txt",
                  inputs: ["build/first.txt"])
action(second) {
  fs.write("build/second.txt", fs.read("build/first.txt") + " second")
}
```

Use `deps: [first]` when expressing target intent directly. Either form creates
the necessary order; using both is allowed and duplicate prerequisites are
deduplicated for scheduling.

## 8.4 Outputs and write directories

The Rattscript declaration interface supplies one output per target. The
scheduler creates its parent directory before running the action and verifies
that the output exists afterward. A command that exits zero but omits the output
fails with `E_ACTION`.

With sandboxing enabled, Rattscript filesystem mutations must stay within the
output's containing directory. For output `build/result.txt`, writing
`build/detail.txt` is within that scope, but writing `source/generated.h` is not.
Normalized traversal such as `build/../outside.txt` is rejected, as are writes
through symlink ancestors.

The declared output is the only one whose content is recorded for this rule.
Ancillary outputs need separate modeling if downstream work depends on them.
Avoid parallel actions that share undeclared intermediate filenames, even if
their declared outputs are different. The graph orders known prerequisites; it
does not infer conflicts between arbitrary writes in the same directory.

`sandbox: false` bypasses the action's Rattscript write roots and backend
subprocess restrictions. The repository uses it for its DUB runtime bootstrap,
which needs to populate external compiler/package caches.

## 8.5 Native graph identity

The graph contains artifacts and named actions. Conceptually actions connect
input artifacts to output artifacts; the DOT presentation uses box-shaped
action vertices to make those connections visible.

The identity calculation includes:

1. A source artifact's normalized path and BLAKE3 content hash.
2. An action's canonical recipe, including commands, captured code/settings,
   working directory, output paths, toolchain identity, and execution flags.
3. The identities of its inputs and prerequisite actions.
4. Each generated artifact's path and producer action identity.

Thus a recipe or upstream identity change can propagate through downstream
action identities even when an upstream output happens to keep the same bytes.
Absolute context/tool paths and captured settings contribute to recipes, so a
graph/cache should not be assumed independent of checkout location or machine
configuration.

Package-tree identity uses SHA-256 and is a separate mechanism; see
[chapter 13](13-registries-and-archives.md).

## 8.6 Native incremental cache

The native cache is stored at:

```text
<build.cache_dir>/graphs/<BLAKE3-of-graph-root>/cache.msgpack
```

For each named action, it records a recipe/input key and hashes of declared
outputs. An action is current only when:

- Its key matches the previously successful entry.
- All declared outputs exist.
- All output contents match their recorded hashes.

Input files are re-hashed; timestamps alone do not decide native freshness.
Changed/deleted outputs are also detected. Cache data is written atomically
after successful actions, and unreadable cache data is treated as a cache miss.

There is no CLI `--force` or remote-cache service. Remove outputs, use `clean`,
or change tracked recipe/input state to request rebuilding. Package caches are
outside this graph cache and are not cleared by `rattbuild clean`.

The cache does not automatically track ambient environment, undeclared reads,
or every tool called from an action. Sandboxed actions use a captured default
environment plus explicit `env:` overrides; that map is part of the recipe.
Automatic compiler actions fingerprint their selected tools. Deferred actions
additionally capture configured C/C++/D tool fingerprints when available;
declare other programs in `tools:` and generator scripts in tracked inputs.

## 8.7 Ordering and parallelism

The graph must be acyclic. Unknown prerequisites raise `E_TARGET`; cycles raise
`E_CYCLE`. With selected target names, only those actions and their prerequisite
closure are scheduled after whole-project graph construction succeeds.

The scheduler chooses ready actions in deterministic graph order and executes
them on a bounded pool of system threads. As an action completes, its dependents
can become runnable without waiting for unrelated work to finish a batch.
The coordinator collects logs per action. Commands inside one action execute
sequentially. Larger job counts increase action-level concurrency, not
concurrency inside an individual compiler declaration.

Undeclared nested projects can mark affected work serial because identities and
resource scopes were not established independently. Correct monorepo
declarations restore normal graph independence; see
[chapter 11](11-modules-and-monorepos.md).

## 8.8 Dry runs

```sh
rattbuild build --dry-run
```

Construction and freshness checks still run. Stale actions are printed as
`would build NAME`, but execution and cache updates do not happen. The summary's
built count is prospective. Generated inputs that do not yet exist are not
created, so a preview cannot substitute for an actual successful build.

## 8.9 Save, visualize, import

```sh
rattbuild graph --json -o graph.json
rattbuild graph --dot -o graph.dot
rattbuild graph --import graph.dot --json -o restored.json
rattbuild build --import graph.json
```

JSON uses graph format version 2 and stores root, project name, actions, and
artifacts. Action records include captured environments, tool hashes, and
strict-execution flags. Import validates producer relationships and recomputed
identities.
It initially uses saved source hashes for validating the serialization; native
`build --import` then refreshes input content before scheduling.

DOT includes a `// rattpack-v2:` line carrying Base64-encoded canonical JSON.
The visible edges are a visualization; the payload is the reimportable graph.
Editing only visible labels/edges does not edit that payload. Removing the
payload makes the file unsuitable for Rattpack import.

Imported graphs do not require their original `Rattspec` files. Execution still
requires source inputs, tools, captured runtime bindings, and the compatible
Rattpack host. Paths retain their saved root/working directories; graph import
is not an automatic relocation operation.

Exporter-specific freshness behavior differs from the native scheduler. See
[chapter 14](14-exporters.md) before assuming another build system performs
Rattpack's output-content checks on every build.

## 8.10 Strict graph execution

`rattbuild build --hermetic` additionally checks declared Rattscript reads and
writes, frozen source/tool bytes, and subprocess tool declarations. A graph
captured with `rattbuild graph --hermetic` retains those action flags when
imported or exported. Strict execution rejects `sandbox: false` and reports
contract failures as `E_HERMETIC`.

Pure Rattscript actions using the embedded libraries can run strictly without
an external process sandbox. Subprocess support depends on the backend.
[Chapter 25](25-hermetic-builds.md) covers both paths and input-change handling.
